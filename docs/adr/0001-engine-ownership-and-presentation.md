# ADR E1: adopt a VT core, own the terminal contract and presentation

> Superseded direction: [ADR E4](0004-owned-agent-native-engine.md) chooses ownership. This ADR preserves the prior rationale/input veto and invariants; it is no longer the active adoption or next-SDK recommendation. Historical X4/EA1 remain FAIL.

[Assessment](../engineering/19-engine-build-adopt-redesign-assessment.md) · [Prior baseline](../architecture/10-recommended-baseline-and-adrs.md)

Date: 2026-10-15. **Accepted-for-design:** one canonical interpretation owner and semantic/cell presentation for both initial frontends. **Recommended next prototype:** official pinned libghostty-vt C API. **Pending:** production adoption, complete compatibility, real rendering/accessibility, resources and upgrade gates. The subsequent [EA1 worker](../engineering/21-ea1-native-worker-results.md) establishes a bounded Rust/public-C seam but **fails required legacy control aliases**; dependent app work is stopped.

The completed [ADR E3 investigation](0003-legacy-input-public-policy.md) finds no safe public policy seam for this correction at the evaluated pin. This recommendation remains conditional; no engine switch, requirement weakening or EA2 progression has been accepted.

The old xterm 6.0.0/serialize 0.14.0 replica model remains a failed candidate: X4 is unchanged and independently nonzero. Those failures establish unsafe serializer continuation; they do not establish broken canonical parsing. A live canonical xterm plus semantic rendering and authorized complete interpretation replay passes the bounded shared-state model. It remains a credible fallback, with unproven complete key encoding and substantial renderer cost.

Recommend libghostty-vt at commit `22fa134a07f5749edd9e92c6bc17d8aaf61843be` for the next phase because its public C API supplies cells, terminal-derived input encoding and a tested snapshot path without our adopting private parser internals. It is development API/format software, not a stable ABI promise. The assessment's six shared continuation cases and five extra state cases pass same-build snapshot continuation; this is necessary evidence, not full-engine certification.

Both Electron and Ratatui views consume revisioned immutable cells/graphemes/styles, geometry, cursor and bounded history pages through the public broker. The Electron terminal surface will be Project X rendering with an explicit accessibility tree, not a second xterm parser or Ghostty's application UI. Canvas/WebGL acceleration with a semantic DOM representation is a prototype direction; renderer technology remains measurement-gated. Host TUI fonts/widths/accessibility remain host-dependent. Preserve the excellent ordinary-terminal requirement; a text inspector or inaccessible canvas does not qualify.

One native worker owns each terminal interpretation and encoder state. Rust broker owns authority, leases and receipts; keepers own PTYs/process facts. Native agents and both clients share one input path. Generated terminal replies have a separate fenced lane; frontend focus never chooses a session implicitly. Restored state does not acquire writer authority. No direct frontend C API/private IPC/persistence/PTY access.

EA1 adds one justified binary-only experimental Rust engine package for the unsafe FFI/process boundary; other crates keep unsafe forbidden. No runtime sandbox or shipping adoption follows. Small private engine DTOs belong in a clearly internal namespace of the existing protocol crate, with separate generated private schemas, client import bans and runtime endpoint authorization. This deliberately revises the earlier service-only private-DTO ownership to avoid copied Rust contracts; it is not a public API. Do not create an FFI crate, wrapper crate, wire crate and worker crate independently. The assessment left six Rust/four TS packages unchanged; subsequent EA1 has seven Rust/four TS packages. The Node engine-host and xterm adapter remain assessment/reference packages; the recommended shipping path would need desktop + protocol TS packages and no separate Node runtime for TUI-only use. Before retiring reference packages, move frontend input/frame types into public generated protocol bindings and check both clients. No reference package deletion/migration has occurred.

Build Project X's renderer, evidence/observation schema, input admission, checkpoint envelope and compatibility harness. Adopt VT semantics first. Do not start a complete VT implementation merely because a screenshot serializer was incomplete. A maintained fork or owned semantic engine remains a funded strategic option if repeated API/upgrade/security or compatibility gates fail; effort alone does not veto it. Estimates, triggers and kill criteria are in the assessment.

This supersedes ADR-A1/A2's Node/xterm browser-replica technology choice and its preference against owning a renderer; it does not weaken product fidelity, input, accessibility, capture or dual-frontend requirements. Original X4 stays available and the existing CI marker remains blocking while broader product gates are open. A later reviewed product-gate replacement must explicitly retire that obsolete candidate criterion, not reinterpret its result as PASS. Existing private-entry/patch budgets remain in force for adoption; a long-lived fork requires an explicit new ownership/budget decision.
