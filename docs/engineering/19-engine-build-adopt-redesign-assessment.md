# Engine assessment: build, adopt or redesign

[Index](../index.md) · [Prior results](18-foundation-gate-results.md) · [Ownership decision](../adr/0001-engine-ownership-and-presentation.md) · [Continuity decision](../adr/0002-terminal-continuity-and-checkpoints.md)

Date: 2026-10-15. **Completed bounded assessment; no production engine or dependent application implementation.** Verdicts below refer to the tested cases and identified design costs. They do not certify a terminal, frontend, sandbox or recovery system. The original X4 fixtures, oracle and independent failing target are preserved.

## Executive recommendation

**ADOPT a VT core and BUILD our terminal platform, presentation and lifecycle contracts. Recommend pinned official libghostty-vt for the next prototype. Do not start a from-scratch VT core now.** It is worth investing substantially in owned rendering, exact observations, input admission, checkpoint envelopes, accessibility and conformance infrastructure: both alternatives need these, and they directly support the product. Owning the entire parser/state implementation becomes worthwhile if the explicit API/compatibility/upgrade triggers below occur and a dedicated team is funded. Effort alone does not reject ownership; the current evidence favors avoiding semantic duplication while buying those capabilities through a public core API.

The best next baseline is one native canonical owner, libghostty-vt through an isolated public C boundary, Rust supervision/keeper/client/TUI, and Electron/TS human frontend with Project X cell/semantic rendering. The current source is development software; production adoption is **pending gates**, not implementation-proven. This deliberately accepts renderer ownership, reversing the earlier cost preference for an xterm browser surface. An excellent ordinary terminal, two initial frontends and core agent navigation remain required.

**REDESIGN xterm** is a viable fallback for screen continuity: keep one headless parser and render its immutable cells in both frontends. It passes all six independently checked canonical continuations and complete-authorized-history reconstruction in this bounded model. That does not repair serialize 0.14.0, provide a complete checkpoint, solve key encoding, or implement a real renderer.

The earlier result rejected **serializer-based replica continuation**, not xterm parsing or the product. Both tested canonical cores meet the hand-authored cursor/text oracle on the six original cases. Ghostty additionally passes same-build binary snapshot continuation, public mode-aware representative keys and five extra state cases. Those are materially stronger seams, with real maturity and integration risks still open.

## A — redesign xterm around one owner

Keep the exact verified family: browser/headless 6.0.0 and serialize 0.14.0 from commit f447274f430fd22513f6adbf9862d19524471c04. The unchanged serializer proof is retained only as a negative regression; neither frontend uses its output as complete engine state. Headless parser/cell access and public-mode observations remain real tested seams; relevant source/declaration evidence is in [17](17-xterm-adapter-risk-and-gates.md).

The design changes materially. A Node engine owner ingests all observed PTY bytes/ordered resizes, agents observe coherent detached cells, and **both** frontend surfaces render those frames. Electron would need an owned renderer/accessibility/selection/input stack instead of xterm's normal browser parser/renderer. Host TUI already needs cell presentation, so its architectural change is smaller. A “custom render addon” is not assumed to make xterm a state-free drawing API; its documented surface still belongs to its own terminal state. Do not sneak in a replica parser, replay unlimited history to make it look correct, or label a text inspector a compatible terminal.

Late attach and frontend restart can read a new bounded canonical frame while the owner lives, including when capture is off. Frames carry session/incarnation, interpretation/profile, prefix, geometry, buffer and mapping generations. Deltas require the exact base; missing updates cause a fresh bounded snapshot, not speculative local repair. Full repaint loss can be a presentation failure without losing canonical interpretation. Pages/scrollback are capped, immutable and explicitly incomplete after eviction. Ordinary shell/editor fidelity, fonts, wide cells, mouse/selection and accessible reading require genuine rendering work and tests.

**Input remains a blocker.** The inspected private evaluateKeyboardEvent helper covers normal/application arrows, selected modifiers, Tab and function keys; it lacks a complete public headless key contract. Pure text/paste and explicit raw fallback do not satisfy required structured navigation. A single owned versioned encoder plus sufficient authoritative mode APIs could solve this, but no separate guessed maps per frontend. The public mode subset does not establish all DECBKM/modifyOtherKeys/NumLock/enhanced-key flags. Any needed upstream exposure must fit the existing two-entry/two-file, two-patch/200-line budget; otherwise reject adoption or explicitly choose a funded fork. Full enhanced protocols may be negotiated unsupported; mandatory conventional navigation cannot be waived. [Pinned helper](https://raw.githubusercontent.com/xtermjs/xterm.js/f447274f430fd22513f6adbf9862d19524471c04/src/common/input/Keyboard.ts)

Replies originate only at the live feed-only owner, tagged by parse event/generation. Cell views cannot generate terminal replies. Replay into a fresh interpreter must suppress historical replies and side effects; identical bytes are not a deduplication key. Native agent/API and human intents share admission; browser generic onData and outer TUI bytes never bypass it. The current fixture replay is interpretation-only and contains no query effects; actual reconnect reply fencing remains untested.

Complete authorized bytes/options/resizes from a known start can reconstruct interpretation. A retained framebuffer, filtered history, gap, wrong width profile or incomplete prefix cannot. No bounded full xterm checkpoint was established, so owner crash without valid retained state/history stays unknown. No-capture recovery does not silently become disk capture. Node GC, observation copies, large synchronous parser calls and total renderer/session memory still need G6 measurements. There are no A latency, throughput or many-session RSS measurements here. Verdict: **credible redesign/fallback; bounded canonical model PASS, full keys/rendering/maintenance gates OPEN.**

## C — own an engine, with an explicit investment case

“Own engine” is not one indivisible project. Parser/state/input, headless observation, drawing, process management and checkpoint policy have different costs and lifetimes. Building the entire stack from scratch would duplicate solved work; owning a coherent terminal contract and renderer does not require owning every lexer or PTY wrapper.

| Component | What ownership buys | What must still be reused/owned |
| --- | --- | --- |
| VT lexer/parser | Explicit bounded FSM/continuation, precise events and compatibility changes | ECMA/DEC behavior and real-terminal quirks; reuse a standards parser unless there is a reason not to |
| Terminal state and input | Direct snapshots, modes, evidence cuts, profiles and deterministic transitions | Both screens, saved state, cells/graphemes, reflow, queries, all accepted input profiles and version migrations are our responsibility |
| Headless API | Immutable renderer-independent observations, generations and exact unsupported/unknown results | Broker authorization/process identity remains separate; never infer application semantics from cells |
| Rendering | Coherent frame model, fonts, selection, keyboard/IME and accessible chrome for Electron/TUI | Browser/OS text and accessibility infrastructure; outer TUI terminal controls its own fonts/widths |
| PTY/process/runtime | Owned lifecycle receipts, process groups, Linux/remote/port boundaries | Reuse kernel interfaces and runtime tooling; a parser is not process recovery or a sandbox |
| Checkpoints | A schema we can evolve and validate with explicit loss/capture semantics | Complete semantic and parser state, safe migrations, storage integrity/consent and reconciliation still need engineering |

### Three credible ownership routes

1. **From scratch:** own lexer/FSM, terminal model, input encoders and all diagnostics. Strongest control of state serialization, allocator/cancellation design and public APIs. Highest compatibility risk; a clean abstraction does not recover undocumented historical behavior. It can be rational for a long-term terminal infrastructure business with a funded core team, especially if desired semantics fundamentally conflict with existing engines. Passing these six fixtures would barely start that program.
2. **Reuse a maintained standards parser, own the semantic engine:** recommended C route if ownership becomes necessary. Rust vte is a credible lexer/action dispatcher; the inspected manifest is 0.15.0, Apache-2.0 OR MIT. It does not implement the complete terminal model, drawing or input encoder. Its private parser state includes partial UTF-8/OSC data; a serde feature does not establish portable Parser checkpointing. Negotiate/export bounded parser state or carry a small reviewed parser fork; do not reconstruct it from visible cells or buffer an unlimited unfinished string. [Manifest](https://raw.githubusercontent.com/alacritty/vte/master/Cargo.toml), [parser contract/source](https://raw.githubusercontent.com/alacritty/vte/master/src/lib.rs)
3. **Maintain a fork of a complete engine:** fastest ownership of proven behavior; a Ghostty or other permissively licensed core could expose the needed state contract. Own all carried patches, upgrades, source/notices, regression triage and vulnerability response. Public C API suffices for the proof, so a fork has no demonstrated necessity today. A permanent fork is a new funded decision outside the existing adoption patch budget; it cannot be hidden as a thin adapter. Upstream contribution is a future human/legal choice, not authorized contact/publication here.

The strongest counterproposal to B is a **maintained xterm fork with a genuine complete-state/encoder API**, retaining its established browser renderer and accessibility machinery. It is more credible than writing a whole VT core merely to save a screen. It could reduce frontend work substantially; that benefit is not measured here. It would own the checkpoint schema across parser continuation, buffers/saved state, tabs/margins/modes, Unicode and device state, plus reply-origin plumbing and upgrades. A second browser parser can be a non-authoritative replica only after future-state equivalence is proved; suppressing replies alone is insufficient. This is a BUILD/fork investment with an expanded explicit maintenance budget, not A's public-core cell-rendering redesign or a two-line serializer fix. No such fork was built.

B is preferred now because an unmodified official public API already passes the state/key proof; that minimizes owned core divergence while accepting renderer cost explicitly. If EA2 shows owned rendering/IME/accessibility dominates total cost, compare one funded xterm-fork seam proof before a semantic-engine rewrite. A planning allowance of two experienced engineers for 4–8 weeks could test exporter/encoder feasibility, without promising full compatibility; qualification still uses the complete-core-fork envelope below. Require full continuation/Unicode/resize/query origin tests and an upgrade rehearsal. A fork that only makes these six fixtures pass does not win.

Standards are a foundation, not a compatibility oracle. ECMA-48 defines control functions; DEC/xterm/modern protocol behavior and real applications extend them. Unicode grapheme segmentation and cell width are separate; fonts/applications can disagree. [ECMA-48](https://ecma-international.org/publications-and-standards/standards/ecma-48/), [Unicode segmentation](https://www.unicode.org/reports/tr29/), [Unicode width](https://www.unicode.org/reports/tr11/), [xterm control sequences](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html), [Kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/)

### Owned state and event design we would require

Use a single ordered interpretation reducer consuming byte chunks, resize/options/profile events and explicit policy-safe device data. Chunk boundaries cannot change meaning. Parser work yields typed bounded reply/side-effect proposals; exactly one current owner may submit them to the separately fenced broker lane. Event IDs, not byte equality, identify repeated identical replies. Restoration does not execute commands, reopen files or resend old device replies. Timers, synchronized-output expiry and host/device responses become explicit ordered inputs where they affect interpretation. This can support reproducible **interpretation under a pinned event history**, never deterministic application/OS execution replay.

A complete-state schema must cover both primary/alternate screens and their contents/history; active/saved cursor and attributes/charset state; margins/origin/scroll regions; tab stops; pending wrap and reflow/line metadata; insert/wrap/reverse-wrap/erase/protection states; colors/palette, links and accepted metadata; keyboard/mouse/focus/paste/enhanced-protocol stacks; Unicode version, grapheme cluster contents/width/spacers; partial UTF-8 and CSI/OSC/DCS/APC state; bounded accepted protocol payloads; options, dimensions and event prefix. Host callbacks, pointers, grant/lease tokens and kernel handles must not be serialized as terminal authority. Every admitted state-affecting feature adds fields or an explicit unsupported boundary. Memory-layout dumps/deriving Serialize on convenient structs do not establish this contract.

Keep versioned tagged fields, strict lengths/counts, total geometry/history/payload limits and explicit unsupported required features. A decoder validates before expensive allocation and restores into a detached untrusted context; only a successfully reconciled instance can become canonical. Test encode→decode→adversarial continuation, not just an equal screenshot. Record checksums for corruption, authenticated provenance/authorization for trust, and migrations that preserve unknown/expired evidence. Preserve old interpretation versions/decoders where retention demands it, with explicit security/EOL handling. Test loss at every snapshot/tail/receipt cut.

Unicode work includes incrementally split UTF-8, combining sequences, emoji/ZWJ/variation selectors, ambiguous/CJK widths, wide-cell overwrites/erases at margins, cursor movement through spacers, wrapping/reflow/resize and scrollback anchors. Pin tables/license/profiles and differential-test with known references; majority agreement is not truth. The host TUI cannot force its outer emulator or a legacy application to use the same width policy. Unsupported combinations need honest capability status and accessible fallback, not fabricated alignment.

Input work includes physical/logical/text distinctions, layouts/dead keys/IME, aliases, Escape timing, cursor/keypad and mode 1035, modifier/function keys, kitty/modifyOtherKeys negotiation, mouse coordinates/focus reports, bracketed paste and validation of embedded delimiters. Keep one encoder shared by native agents and normalized human intents; outer TUI key information may be irrecoverably absent. Input receipts remain non-idempotent; observe–act–observe and generation checks reduce races but cannot freeze an opaque application's widget state. Ctrl-C is input, not proof of termination. Password/approval contexts cannot be universally recognized in opaque output.

Security work includes bounded OSC/DCS/graphics and grapheme growth, integer overflow/huge resize, reply amplification, pathological CPU, snapshot corruption/decompression/allocation bombs, stale borrowed references and parser fuzzing. Default clipboard/window/file/network actions stay denied; unknown sequences are data. Never let repository plugins install arbitrary parser code. A same-user host can still bypass mediated input; enforced runtime containment and process groups remain separate projects. Human takeover revokes future mediated admissions and reports remaining effects, not universal cessation.

Ranges include conformance and fault work, not merely drawing a shell. Fractional design/accessibility/security support is required in addition. Recruiting, missing expertise, broad platform support or a fully stable archival format can exceed the ranges.

These are alternative estimates for core work, not totals to add together. **Both** leading choices still need owned frontend rendering/accessibility and real PTY/lifecycle integration. For an own-core terminal subsystem with polished Electron + host TUI, allow roughly **6–9 engineers over 18–36 months**, combining parallel core, renderer, platform and conformance work; this is a broad funding envelope, not a schedule derived by adding the table rows. Tasks/artifacts/agents, runtime isolation, durable approvals, remote helpers and full macOS/Windows qualification are outside that envelope. A one-person six-fixture prototype can be much quicker and proves much less. Money depends on actual location/compensation/contracting; no salary or budget claim is invented here.

Long-term ownership pays when terminal behavior/state contracts are strategic IP, stable forensic snapshots are mandatory across supported versions, unusual navigation/Unicode/inspection requirements cannot be exposed safely, or recurring vendor changes/backports exceed a funded ownership cost. Adoption pays while the public boundary covers those needs and a supported frozen engine tuple plus tested envelopes is sufficient. One missing serializer feature alone does not justify 27–180 core person-months. Conversely, a team explicitly prioritizing independence can rationally choose C with this budget and a compatibility profile; it should not pretend a lightweight fork/adaptor is the same undertaking.

## Continuity and capture contract

| Event | A revised xterm | B public Ghostty core | Owned core | Product rule |
| --- | --- | --- | --- | --- |
| Late view attachment, owner alive | Fresh immutable bounded cells, no replay needed | Fresh cells/render state; no clone needed | Same public frame contract | No capture consent needed for bounded live memory; renderer fidelity still required |
| Frontend restart/disconnect | Owner can continue; drop old unsent input and reobserve | Same | Same | Fresh mapping/lease handshake; no stale focus or grant resurrection |
| Engine owner crash, no valid surviving state/tail | Interpretation unknown | Snapshot API alone cannot resurrect lost memory | Owned codec cannot resurrect absent bytes/state | Input disabled; separate process controls and new session remain available |
| Engine crash with surviving valid memory checkpoint+tail | No complete xterm checkpoint established; complete retained initial history is a possible bounded case | Same-build state restoration is promising | Explicit state codec can support it | Must prove exact cut/tail/gaps and failure-domain survival; not implemented here |
| Engine crash, authorized complete capture | Reinterpret from a known start, suppress historical effects | Snapshot+tail or full interpretation history | Versioned state+tail/history | Capture must be complete/compatible; filtered/gapped data is insufficient |
| Keeper/PTY/process loss or reboot | Parser state does not restore processes | Same | Same | Observe exit/unknown outcomes; never rerun actions automatically |
| SSH/helper disconnect | Transport/runtime-dependent | Same | Same | No remote process ownership inferred from a terminal image |

There is no requirement to guarantee impossible power-loss recovery while persisting no recoverable state. No-capture owner loss was already allowed to become unknown in the prior design; maintaining that explicit limitation is not a newly weakened requirement. Frontend restart and late attach **are** required without disk capture and must not depend on complete historical replay. Ghostty snapshot support improves possible recovery mechanisms but does not change consent defaults. Snapshots can contain secrets and raw-equivalent state; storing them requires the appropriate explicit consent and retention. Plain “filtered output” consent cannot authorize raw checkpoints. [ADR E2](../adr/0002-terminal-continuity-and-checkpoints.md) owns the envelope, admission and cut requirements.

## Cross-cutting decision matrix

| Requirement | A redesign | B adoption | Owned semantic core |
| --- | --- | --- | --- |
| Agent correctness / exact observations | Canonical model demonstrated; full key/mode seam open | Canonical + key/snapshot subset demonstrated | Most control, with most correctness still to establish |
| Fidelity / accessibility | Proven parser does not supply our new renderer; Unicode profile and accessible view unqualified | Mature parent behavior helps; public cell/render APIs do not supply accessible Electron/TUI UX | Full compatibility/text/a11y obligation remains ours |
| Dual frontend parity / ordinary terminal | Same frames/intents feasible; real keyboard/font/IME/host tests missing | Same; native worker can serve TUI without Node engine runtime | Same contracts; cannot recover keys the outer host never reports |
| Memory / latency / many sessions | Node/GC/copies/renderer costs; no G6 measurements | Native allocation/snapshot/callback stalls; no G6 measurements | Maximum scheduling design control, no automatic speed or safety advantage |
| Human takeover / permission boundaries | Broker responsibility, not parser behavior | Same; C callbacks must not own host authority | Same; custom core does not solve uncontrolled host writers |
| Recovery without capture | Live-owner view recovery; owner loss may be unknown | Same, with possible bounded surviving-memory snapshot/tail | Same physical limits |
| Extensions / upgrades | Narrow adapter and constrained input exposure; private-budget risk | Development C API/codec version churn, stronger public surfaces | We own schema and every migration/security fix |
| Total cost | Lower core migration, substantial owned rendering/input | Best current core seam; still substantial renderer/FFI qualification | Highest strategic control and staffing commitment; fork reduces initial semantic rewrite |

**Nonnegotiable:** two initial useful frontends, accurate visible fidelity for advertised profiles, renderer-independent agent navigation, one authoritative reply/input path, explicit identity/lease/freshness, unknown/partial outcomes, bounded resources, truthful capture and recovery, no universal opaque-TUI semantic claims. No candidate gets to bypass them because it passes six fixtures.

**Owner choices:** acceptance of a pinned development SDK; exact feature/Unicode/graphics profile; consent to raw checkpoints; funding a custom renderer or full engine team; initial host/platform certification breadth; retaining older interpretation builds versus explicit unsupported-history status. Our recommendation chooses owned rendering and a conditional public-core adoption. It leaves release acceptance of an unstable SDK and complete archival compatibility open. A GTK-only product or postponing the host TUI would change the requested product, so neither is used to force a green result.

## Reproduction, gates and adversarial self-review

```sh
make bootstrap docs-install install
make assessment-bootstrap
make assessment-build
make assessment-check
make verify
make engine-gate   # expected nonzero: original failed model remains independent
```

No public server is started. Bootstrap fetches exact official compiler/source digests, verifies existing source without overwriting it, and leaves build dependencies to the pinned upstream manifests/cache. `assessment-command.py` records exact argv, project-local environment overrides, versions/provenance through companion records, duration, exit, bounded stdout/stderr and fixture/source hashes. Command PASS means exit 0; candidate proof PASS additionally requires assertions. Build duration is not terminal performance. The complete latest evidence inventory and checks are recorded at the end of this session.

Proof outputs: `xterm-assessment.json`, `ghostty-assessment.json`, `ghostty-source.json`, `ghostty-source-correspondence.json`, `zig-tool.json` and `commands/*.json` inside `evidence/engine-assessment`. Original evidence is in the verified archive and unchanged legacy fixture/oracle. No source-family change is hidden in an npm/Cargo lock refresh.

Self-review challenged these conclusions and corrected the following:

- **Wrong causal diagnosis:** retained X4's serializer failure but independently checked canonical parser outputs; did not generalize it into a parser/product failure.
- **Reply chunking oracle:** compare exact concatenated DSR response bytes; callback counts are recorded rather than required as query counts. A future valid split/coalesced callback must not be misclassified as a parser defect. Broker emission IDs can use work ID + callback ordinal without byte-based deduplication.
- **Callback oracle:** a counter initialized after decode cannot observe decode effects. Replaced it with the already installed source reply callback count across decode and a query before rebind; tested no inherited callback and two fresh replies after explicit rebind. This does not prove suppression of every possible callback/effect.
- **Tautological UI claims:** marked copied frame agreement as a model, not real renderer, accessibility or frontend parity evidence. Raw grid traversal is not offered as a production render loop.
- **Key oracle bias:** retained initial CR result, inspected mode-1035 behavior and tested both profiles. No hand-coded escape replacement or upstream patch made the test green.
- **Snapshot overclaim:** tested continuation, partial inputs and corruption; still distinguish live copies, encoded terminal state, durable product checkpoints and process recovery. Decoder version rejection is not cross-version support.
- **Capture/authority bypass:** snapshots/raw-equivalent state need explicit consent; no restored focus/lease/grant authority; historical replies/effects must not be reissued. Takeover still cannot stop all side effects.
- **Hidden cost:** explicitly chose owned rendering and an unsafe native seam; retained Electron/a11y/host gates, feature footprint, dev-API churn and engineering estimates. No free performance, stable ABI or cheap complete-state assumption.
- **Overengineering:** no toy engine, production worker, public ABI, plugin system, extra shipping crate or GUI was built. The assessment uses one small C proof through official public headers and existing JS/reference fixtures.

Residual evidence gaps are specific: real render-state throughput and snapshot stalls, Rust FFI/thread/allocator safety, complete key/mouse/IME/layout profiles, real host/desktop accessibility, full Unicode/graphics/terminal compatibility, hostile decoder/parser fuzzing, all-process G6, actual crash/tail consistency, cross-version/architecture state portability, supply-chain release clearance and upgrade economics. These block qualification, not completion of this assessment.
