## Order and stopping rules

First prepare only the smallest locked tool/source and fixture foundation, then run PP1 before investing in complete frontends or supervisor. Both initial clients are required; engineering order does not make TUI a later optional feature. Then PP2 and PP3 establish whether the default is a usable terminal within the resource envelope. PP4 establishes honest persistence and process semantics; PP5 establishes restricted execution before the P2 supervision milestone; PP6 tests the actual combined product. PP7 packages only a bounded certified baseline. PP8 is a formative human validation gate with revisions expected. Small teams should pursue one primary stack and at most one targeted challenger for a demonstrated failure, not implement four terminal-engine alternatives. TUI and desktop share one backend/inner engine rather than count as competing stack alternatives.

Each result records exact source/package revisions, machine/OS/display/GPU details, scripts/fixtures, capture authority, observations, failures and residual uncertainty. Never waive a correctness/security failure with an average latency result. A successful spike is not certification of arbitrary applications, hosts, agent models or future dependency releases.

## PP1: falsifying the default early

The initial xterm exploration and subsequent libghostty-vt assessment are complete at bounded scope; [19](19-engine-build-adopt-redesign-assessment.md) records exact evidence. EA1 now has a bounded public native seam with a failed legacy-input selection gate (21). Resolve that gate before EA2–EA4 establish real renderers and recovery/maintenance under ADR E1/E2. Preserve the original X4 oracle and no-capture limits. A private helper, a binary snapshot name or passing six fixtures does not establish a full product API or certification.

The exercise must distinguish logical key encoding, human committed text/IME, paste, negotiated mouse reports, terminal replies, raw fallback and UI commands. Cover application cursor/keypad modes, modifiers/function keys, enhanced keyboard negotiation, bracketed paste, Escape timing, Unicode, alternate screen and resize. Replay fixtures with different chunk boundaries; compare canonical/presentation observations at explicit prefixes. A completed write callback, not an arbitrary frame event, establishes the relevant parser frontier. New views must not send duplicate device replies. Human key handling must not require stealing global browser focus for agent actions.

Require a documented path for presentation reattachment and **separate** complete canonical recovery. Losing a canonical engine in a capture-off session can legitimately produce unknown interpretation; pretending a serializer is a complete parser state is a fail. If a narrow pinned bridge suffices, record its owner, upstream update surface and upgrade procedure. If it requires ongoing terminal semantics maintenance across many private interfaces, stop and compare a single challenger before building the rest. A Ghostty parser alone does not solve rendering, accessibility or the product's UI.

## PP2–PP3: human and resource reference conditions

Use the [G6 reference](07-validation-roadmap-and-risks.md#performance-and-resource-budgets): eight CPU cores, 16 GiB RAM, SSD, 1080p. Record exact CPU/GPU/driver/display scaling; integrated graphics must be represented. Thirty-two sessions/eight active attempts, aggregate 8 MiB/s output for ten minutes, visible terminal plus review UI. Measure end-to-end p50/p95/p99 and maxima for input, paint, decision changes, resize and revocation, not only encoder throughput. Measure canonical parser lag and every application process, including the Rust TUI. Run TUI-only without Electron, desktop-only, then both clients on the same session set. Include controlled outer-terminal/tmux actual paint and end-to-end resource footprint separately from product processes; output flush is not paint evidence. Exclude child tool memory only with separate reporting; include Rust, Node, Electron, replicas, scrollback, queues and evidence-index overhead.

Pass budgets are p95 key-to-paint ≤50 ms, decision update ≤250 ms, future-admission revocation ≤100 ms and application memory ≤1 GiB. Per-session live scrollback ≤32 MiB within a shared 256 MiB; output queue ≤4 MiB/session within a separately measured global bound. Initial global output-queue limit is 128 MiB at 32 sessions, included in the 1 GiB total; admission must tighten the active set if the measured process baseline leaves insufficient headroom. Memory budgets are allocations, not simultaneous capacity guarantees. Disk policies are in ADR-A6. Foreground rendering aims for 60 Hz; record dropped frames and GPU fallback behavior, without turning the target into an absolute device guarantee.

Minimal-shell cold readiness ≤1 second is measured with a declared clean shell fixture; user rc execution is reported separately. Start-up UI must distinguish waiting for a slow shell from an unresponsive application. PP2 includes keybinding collisions, selection under mouse reporting, keyboard-only approvals, screen-reader focus, IME candidate placement, CJK fallback and zoom. Windows/macOS accessibility must later be tested natively, not inferred from Chromium or successful Orca testing.

## PP4–PP6: failures that must remain visible

Fault injection includes before/after input admission and partial PTY writes; process exit races; foreground process-group changes; keepers surviving broker death; engine death during an incomplete escape sequence; stale replicas; disk full/readonly storage; truncated evidence; stale approval after a human edit; connection loss after a one-shot action; model/controller crash; and a noisy terminal starving unrelated sessions. Retries of observation are safe only within their own read contracts; requests with unknown effects require reconciliation.

Default request/receipt reconciliation horizon is 24 hours; declare it to clients and reject expired request IDs rather than treating them as new. Minimal tombstones distinguish expired IDs, without keeping secret input. An action's 180-day metadata policy is distinct from that retry window and from transcript/artifact expiry. Verify privacy against temporary files, indexes, diagnostic logs and process crash-dump policy, not just the main database. Do not submit test secrets or private host paths to an external service.

Runtime negative tests cover writable source mutation versus sealed source, hidden shared Git administration, symlink/path escape, namespace fallback, inherited descriptors, credential/env leakage and unconfined controller paths. A host-side native agent is still a host-authority principal even when its requested children are confined. Native APIs can mediate only their own launches and inputs; a legacy CLI's independent network calls and tools are not automatically supervised.

Takeover tests separately assert future-write fencing, future tool-admission revocation, requested termination, observed exit and residual external effects. Human subjects must identify those differences. Do not present a stopped typing stream as a stopped task, or a killed process group as reversed remote effects. Provider spend estimates are not hard billing caps without provider-side evidence/control.

## PP7–PP8: release and usability decisions

Package one aligned two-frontend/core tuple and one restricted Linux runtime profile. TUI-only installation includes the qualified native engine, with no separate Node engine runtime and must not require Electron or a display server. No public plugin ABI is promised for 0.x. Compatibility failures fail closed for grants while permitting read-only inspection/export where safe. License remains an owner choice until adopted; Apache-2.0 is the recommendation and dependency obligations remain independent.

For PP8, recruit a small formative sample (for example 5–8 operators across terminal-heavy, agent-heavy and accessibility needs); that sample is not statistical certification and does not substitute for expert accessibility testing. Before testing, specify critical tasks: locate a failed dependency without opening every session, identify exact checked revision, deny a stale approval, take input without assuming side effects stopped, recover an unknown action without duplication, and use a terminal with no agents. Record completion time, errors, interventions and confidence alongside correctness. An unsafe accidental approval, wrong-session input or confidently wrong interpretation of unknown execution is a blocking finding. Set task-specific usability thresholds before observing results; do not invent a success percentage after the fact.

## Foundation bootstrap after separate engineering authorization

This ordered plan now governs the authorized bootstrap. Its current stopping point is the failed essential gate, not completion of all steps. Keep each step reviewable and stop at failed essential gates.

1. **Resolve the actual tool/artifact tuple.** Verify compiler/MSRV, supported Node, pnpm policy syntax, terminal artifacts/commit and notices. Record lock/provenance decisions; X1 fails on an unexplained browser/headless mismatch. Create only minimal workspace/harness files needed for the next gate.
2. **Falsify the engine/TUI seams.** Minimal headless feed→canonical cells→Ratatui and browser presentation, typed keys and query replies. Establish X2–X4 minimal continuation/prefix cases and outer decoder limitations within budget. Reject xterm if internals exceed the budget; do not build full product UI to hide failure.
3. **Establish shared contracts and pure rules.** Rust domain/wire source, schema→TS generation, typed errors/cancellation and fake scenario clients. CI1 blocks stale approval/writer/unknown-outcome violations and forbidden dependency edges before adding real authority.
4. **Add owned Linux execution and lifecycle.** Keeper/PTY/job control, bounded engine flow, durable receipts and store; PP4 failure tests distinguish GUI/TUI, broker, engine and keeper loss. No host-side broad-safety promises.
5. **Complete both client vertical slices.** Ordinary shell→pager/editor→review→attach/takeover/detach, shared config and DF01–DF07; actual keyboard/IME/Orca/outer-host evidence. PP2/G8 fail for a missing critical workflow. Collect early load costs before broad polish.
6. **Enable restricted supervision deliberately.** PP5/G4 establishes effective rootless offline controls before P2 claims; then PP6 tests eight tasks, revision review and residual-effects takeover in both clients. Missing prerequisites block strict admission.
7. **Close performance and human gates.** Full PP3/G6 three-mode all-process benchmark and PP8 critical-error tasks, declared fixtures/measurement apparatus and thresholds. No invented latency or small-sample productivity claim.
8. **Package and review release evidence.** PP7/CI4 verifies both artifacts, offline startup, migration/rollback/logout, SBOM/notices/license-owner decision and complete advertised-profile evidence. Later ports/remote helper/128-session work stay outside this foundation.

The actual seven-Rust/four-TS foundation remains bounded, including the experimental EA1 binary worker. ADR E1 proposes two shipping TS packages; reference harness packages are not deleted or called production. [14](14-repository-and-engineering-practices.md) owns the target/current distinction. Unit/property/wire tests precede broad integration, and costly matrices expand only with supported claims.

## Beyond the first certified baseline

P3 adds complete sealed-validation profiles and richer credential/runtime cases. P4 adds helper-backed remote recovery with explicit remote trust and deployment, then native macOS/Windows ports behind their own PTY/process/isolation/accessibility gates. P5 investigates 128 sessions, multi-user authority and fleet scheduling only after profiling and operator studies. No default microservice split, generic workflow engine, marketplace or public native ABI is needed to reach the initial product. A failed early gate can narrow scope; it cannot silently weaken compatibility, evidence or permission invariants.
