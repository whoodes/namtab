## Contradictions and impossible guarantees checked

Compatibility versus confinement: the [profile matrix](../architecture/04-isolation-security-and-approvals.md#filesystem-and-runtime-profiles) preserves host-environment use while declining a host sandbox claim. Worktrees separate edits and share Git administration; sealed runtimes do not expose the common Git directory. Restricted profiles can reject incompatible tools rather than silently pretending the host environment is unchanged.

Exactness versus privacy: [evidence representations](../product/02-work-evidence-and-coordination.md#exact-evidence) do not claim redacted data is original raw evidence. [Snapshots and recovery](../architecture/05-architecture-storage-and-extensions.md#storage-and-durability) cannot persist raw-equivalent terminal state under a filtered-only policy. Missing or expired evidence remains unavailable, even if a historical pass record survives. Secret filtering is explicitly imperfect.

Approval versus arbitrary code: a granted host shell can act without further terminal input. [Permission semantics](../architecture/04-isolation-security-and-approvals.md#permission-semantics) permit narrow per-action guarantees only at an enforceable broker/runtime boundary. Human approval of text is not a proof of program behavior. Spoofable shell markers and terminal output cannot grant authority.

Durability versus side effects: [recovery](../architecture/05-architecture-storage-and-extensions.md#reconnect-and-crash-recovery) distinguishes request admission, dispatch, effect, and result. Unknown outcomes are reconciled, not automatically retried. Database atomicity does not make external actions exactly once. GUI restart, runner loss, remote disconnect, and reboot have different recovery limits.

Terminal interpretation versus application truth: a canonical grid and byte prefix do not reveal a TUI's semantic state. Resizes, output arrival, mode changes, and input delivery are not a universal atomic transaction. PTY streams do not recover descriptor identity, pipe timestamps do not establish total program write order, and alternate-screen snapshots are not command transcripts.

Structured navigation versus universal semantics: the selected encoder can describe logical intent and emitted bytes, not guarantee which application operation consumes them. Legacy aliases, custom shortcuts, Escape timeouts, keyboard layouts, completion hooks, and unknown editor/widget modes remain explicit. Raw input is not a denial bypass. A structured event or bounded batch does not make application state transactional; receive/dispatch checks cannot see all in-flight output or freeze a program. N01–N16 test specific pinned profiles rather than every opaque TUI.

Focus versus ownership: explicit session-targeted input works in a background session without stealing human focus; a request derived from a view instead validates its mapping/focus generation. Neither proves application-internal focus. Human override fences future navigation, while already delivered prefixes and background task effects remain separately accounted for. Terminal selection/paste and sensitive prompt handoff use their own context/capability checks.

Replay versus reproducibility: retained events can rebuild domain projections, and retained byte/geometry history can support versioned terminal playback. Neither promises deterministic execution replay, restoration of dead processes, or frozen external services. Every actual rerun is a new execution with new evidence.

Finite resources versus losslessness: unlimited complete capture, zero producer blocking, bounded storage, and arbitrary output volume cannot all be promised. The design chooses bounded queues and explicit backpressure/gaps, with visible consequences and an independent control reserve. Whole-program stop latency and provider spending are not mislabeled as broker admission guarantees.

## Premature abstraction review

The [module map](../architecture/05-architecture-storage-and-extensions.md#module-ownership-and-extension-seams) is a responsibility/dependency map, not a mandate for a separate service per module. A local modular application precedes distributed placement. Terminal and runtime seams have immediate compatibility/security reasons; generalized scheduling plugins, dynamic UI plugins, a marketplace, universal shell parsing, and fleet orchestration are deferred. The [recommended Rust/TypeScript, initial Ratatui TUI + Electron/xterm baseline](../architecture/10-recommended-baseline-and-adrs.md) now resolves language/engine/toolkit defaults, with PP1–PP3 veto gates; Apache-2.0 remains a recommendation pending owner adoption. One engine host and private 0.x protocol avoid a per-session browser or premature public ABI.

The domain has several distinct objects because their authority and lifecycle differ, not to create a generic ontology. A concrete first workflow can create a task, one attempt, a session/execution, an artifact, a validation, and a decision without implementing every provider type. Initially the private 0.x protocol is pinned to bundled components; prior public-client transition support begins only when a public release contract exists. Exports and migration backups remain required. No permanent plugin ABI is promised.

## Second review in this session: challenges and repairs

This pass read the combined recommendation, UX, protocols and roadmap against concrete operator/failure scenarios. It challenged the chosen stack rather than treating selection as proof. The repairs below are incorporated, and structural checks followed them.

| Challenge | Repair / residual consequence |
| --- | --- |
| Human frontend was less concrete than backend responsibilities | [11](../ux/11-human-experience-spec.md) specifies default zero-agent terminal, four lenses, keyboard routes, focus/selection, rendering/paste/search, windows, attention, trusted approvals, configuration and J01–J08. [PP2/PP8](../engineering/12-prototype-plan.md) can reject this UX; no usability results asserted. |
| “Canonical parser” could hide browser/headless drift, duplicate replies and a direct onData bypass | [A2](../architecture/10-recommended-baseline-and-adrs.md#adr-a2-one-interpretation-authority-replaceable-presentation) makes one reply authority and one bridge mandatory. Public string input is not logical-key encoding. Browser/headless version metadata differ even in the chosen tag. PP1 fails for a sprawling private API dependency or full parser fork. |
| Framebuffer serialization could be mistaken for full checkpoint/recovery | [03](../architecture/03-execution-terminal-and-remote.md#terminal-emulation-and-uncertain-state), [05](../architecture/05-architecture-storage-and-extensions.md#reconnect-and-crash-recovery) and UX now separate replica attachment from canonical recovery. Canonical loss disables all application input including raw fallback; process controls/new-session creation remain. This can lose access to a still-running interactive program and is an explicit residual risk. |
| Keeper survival was worded as sufficient for screen recovery | [05 storage](../architecture/05-architecture-storage-and-extensions.md#storage-and-durability) now requires both keeper and canonical engine survival for volatile reattachment. Capture-off output cannot materialize from disk. Pinned serializer testing does not eliminate this failure boundary. |
| Privacy default, retention and independent evidence reservations disagreed across documents | [A6](../architecture/10-recommended-baseline-and-adrs.md#adr-a6-capture-and-retention-defaults) replaces ordinary disk capture with bounded memory; seven-day opt-in output, 24-hour explicit raw evidence, reserved pins and one shared transcript cap. Control metadata also has a capacity budget/reserve and admission consequences. Retention cuts require a domain checkpoint plus remaining events; this is distinct from terminal checkpoint recovery. Active state survives event ageing, while purged history stays unavailable. No hidden spool/index/crash copy. |
| Restricted execution was recommended but postponed beyond the supervision MVP | README and [P2](../engineering/07-validation-roadmap-and-risks.md#staged-roadmap) now require basic G4/PP5 for advertised restricted tasks. P3 expands sealed input/credential profiles. Host-side native controllers remain host-authority unless independently confined; controller/runtime/workspace badges are separate so one offline child cannot make the entire task look sandboxed. No implicit image pull. |
| Keyboard convenience could steal TUI/IME keys or deliver to a newly focused target | [UX keyboard contract](../ux/11-human-experience-spec.md#three-action-planes-and-keyboard-behavior) reserves a remappable chrome escape, keeps F6 in chrome only, gives IME priority and cancels one-chord forwarding on context change. UI/PTY/automation remain separate routes. |
| Takeover or stop buttons could suggest all side effects stopped | UX reports future revocation, stop requested, observed exit and unresolved writers separately; no “all paused” badge. Resume needs new context/lease; old queues/grants never replay. |
| Critical notifications could bypass the attention budget indefinitely | Critical failures use an aggregated persistent banner, not unlimited toast exceptions. Durable inbox entries survive interruption suppression. |
| Full-load targets could hide duplicated presentation buffers or sum independent allocations beyond total memory | [G6 budgets](../engineering/07-validation-roadmap-and-risks.md#performance-and-resource-budgets) include all Electron/Node/Rust processes, replicas and indexes; shared caps and admission tightening apply. Targets remain unmeasured. |
| A small formative sample could imply statistical productivity or safety proof | [01](../product/01-product-and-supervision.md#product-validation) and PP8 separate blocking formative findings from later adequately designed comparative claims. Task thresholds are predeclared, not invented after observation. |
| A prior-client promise and generic plugin ecosystem were premature | Private bundled 0.x first, executable adapters after demonstrated need, no UI/native marketplace. Upgrade rehearsal and dependency notices are gates, not an excuse for permanent forks. |

Rejected alternatives remain explicit: backend-only omits half the product; all-native/custom rendering expands text/accessibility work; Tauri is not a cure for an xterm API gap; tmux-primary cannot ensure exclusive writers; mandatory hooks break legacy use; worktrees are not isolation; raw-only navigation duplicates encoding logic; universal per-command shell approval and exactly-once/replay guarantees are impossible at this boundary. [06](../research/06-technology-distribution-and-compatibility.md) and [10](../architecture/10-recommended-baseline-and-adrs.md) state when a targeted alternative is justified instead.

Mutable-workspace review also labels the last observed manifest/time rather than claiming a watcher sees every outside write; only the sealed-input profile can offer its stronger binding.

Small-team review: the baseline still has substantial browser/Node/Rust packaging and terminal-seam maintenance. It is feasible only as a hypothesis for a team able to own both languages and upstream updates. PP1's upgrade rehearsal, one stack/profile, native Linux package first, no custom container engine and no public ABI limit that burden. If staffing or PP1–PP3 fail, narrow supported scope explicitly; do not add a fourth language or several engines to save the original recommendation.
