# Native agent, work and observation contract

[Campaign](index.md) · [Core](compatibility-and-core.md) · [Runtime and recovery](runtime-persistence-security.md) · [Human journeys](frontend-contracts.md)

**Proposed native contract for product v1; unimplemented, private experimental wire version pending N0.** The identity, event-cut and fact rules below are the N0-01 contract draft for [issue 7](https://github.com/whoodes/namtab/issues/7); [receipt admission and reconciliation](#receipt-admission-retention-and-reconciliation) are the N0-02 draft for [issue 8](https://github.com/whoodes/namtab/issues/8). Neither is NG0 acceptance or N1 implementation evidence. The existing small domain/protocol tests are useful foundations, not this API's completed implementation. Source rationale: research S02–S05, S15–S19, S31–S32. Policy rules below are namtab decisions.

## Objects and authority

| Object | Identity / lifetime | Meaning and authority |
| --- | --- | --- |
| Principal | Namespace-qualified principal ID + authenticated connection binding + capability generation | Human, agent or adapter role. A display name/process title is not identity. Capabilities narrow operations, sessions, data, runtime/context, retention and expiry. Reconnecting authenticates again; a caller-supplied principal field cannot bind the connection. |
| Workspace/context | Stable context ID + immutable record revision; source manifest and runtime-policy revisions are explicit bindings | Creating or replacing an owned context gets a new ID; changing its recorded configuration creates a revision. A path/worktree name never selects a historical context. Deletion retires the ID. A Git worktree isolates edits, not processes or secrets. Shared writable contexts require an explicit coordination policy. |
| Task | Stable task ID + immutable work-definition revision; separate lifecycle-record revision | `task.revision` binds acceptance requirements, selected dependencies and budget. Definition changes append a task revision; status-only transitions append a lifecycle record without changing that subject. Acceptance remains attached to its reviewed task revision. [Product 02](../product/02-work-evidence-and-coordination.md#state-and-acceptance) owns the state machine. |
| Attempt | New attempt ID per execution attempt + record revision + pinned task/context/dependency revisions | Retry creates another attempt ID, including after unknown/canceled work. An attempt can own several managed executions and refer to several sessions. Its result is separate from process exit and human task acceptance. |
| Session | Stable session ID + incarnation + interpretation/profile revisions | Continuity of one interactive compatibility surface. A new backing interaction target or unproven continuity retires the old incarnation. Several tasks may reference it; no exclusive task ownership is inferred from screen position. |
| Process execution | New execution ID per admitted managed launch + runner ID/incarnation + private OS handle identity | Identity is fixed before launch; launch failure still has that execution ID. Repeating argv gets a new execution ID. Pipes or a fresh PTY are selected at creation. PID, cwd and prompt do not identify it. Child status and stream observations are facts within the runner's visibility. |
| Operation | Service-issued operation ID + authenticated request identity/binding + authority epoch | One admitted mutation and its reconciliation record, independent of whether it has a session event. The request identity belongs to its authenticated principal/issued namespace. Reusing it with different data conflicts while the binding is available; missing binding refuses repeat submission. [N0-02](#receipt-admission-retention-and-reconciliation) owns admission/retention. |
| Observation | Immutable observation ID + typed subject + event cut + semantic/geometry/profile revisions + completeness | A captured projection of what the authorized component has processed. Re-reading its ID returns that cut or unavailable, never a newer view under the same ID. It does not prove the application will remain in that state. |
| Artifact / validation | Artifact ID + immutable content revision; validation ID + exact subject/context/check/evidence bindings | A new edit/publication produces a new artifact revision; immutable revision identity is separate from its authorized content digest. Validation cannot silently follow latest. Producer attempt/execution and capture ranges remain inspectable. An exit code is not artifact correctness. |
| Decision | Decision-request ID + revision + exact review subject; recorded decision ID + authenticated disposition | Pending, superseded and recorded dispositions are explicit records. A changed task/artifact/validation selection needs a new current review; historical decisions remain historical. Acceptance is a domain transition, and permission grants have their separate broker lifecycle. |
| View / writer lease | Endpoint/view IDs; focus generation; writer and sizing epochs | Focus identifies a human interaction destination; authority permits a bounded action. Native agents address sessions explicitly and never acquire desktop focus implicitly. |

### Reference, revision and lifetime rules

An object identity is `(namespace_id, object kind, id)`. The service issues an opaque namespace and IDs; namespaces are never reassigned after store reset/clone or loss of identity continuity. A verified restart may retain the namespace, while issuing a fresh **authority epoch** before admitting mutations. An authority epoch fences grants/control; it does not rename historical objects or prove process continuity. IDs are nonsecret locators, not bearer capabilities. Authorization is checked on every dereference, including historical reads, without revealing denied objects' existence.

The draft identity bound is 1–128 ASCII bytes matching `[A-Za-z0-9][A-Za-z0-9._:-]*` for namespace/object IDs. Clients treat the entire value as opaque, including the readable synthetic labels below. Revisions, incarnations, epochs, event numbers and byte offsets use canonical unsigned decimal strings (`0` or a nonzero digit followed by digits, at most 20 digits and at most `18446744073709551615`), never JSON numbers. Revisions/incarnations begin at `1`; event/byte cuts may be `0`. Exhaustion refuses further allocation rather than wrapping or reusing identity. N0-06 must carry these identity semantics into a separately versioned public schema; these examples do not adopt an existing public-v1 or EA1 namespace.

References in an envelope inherit its `namespace_id` unless they explicitly name another namespace; their field/type identifies object kind. They must include the exact revision or incarnation when binding a mutation, validation, dependency or evidence subject. A current-state read uses an explicit `selection: "current"`; it must return the resolved reference. Omitting a revision is not permission to follow latest. A revision identifies an immutable record and is ordered only within that object; it is not a content hash or another object's clock. Record revisions, terminal semantic revisions, geometry revisions and interpretation/profile versions are separate typed fields. A task lifecycle record has its own revision and names the task definition it describes. Transition admission compares that expected lifecycle revision as well as the exact task/review subject; changing ready/active/awaiting-review/accepted status does not stale an unchanged definition or a pinned attempt. A changed definition does require a new current review. This distinguishes subject currentness from lifecycle compare-and-set; it does not select N0-02's receipt algorithm.

Sessions keep their incarnation across frontend attach/detach and a verified live-owner reconnect. Replacing a shell/PTY, restarting a session or losing target/interpretation continuity without a valid reconciliation retires that incarnation; any replacement gets a strictly new one and fresh ownership. Unknown interpretation fences application input while recovery is evaluated; it is not cured by incrementing a counter. Exact state/tail recovery and surviving-runner reconciliation are governed by [runtime recovery](runtime-persistence-security.md#precise-v1-recovery-contract), and are not implemented by this draft. Runner incarnation changes whenever that runner is replaced; a surviving process may be associated again only by verified stable OS-handle evidence, never by PID reuse. A new launch always gets a new execution ID.

Deleting a context, session or artifact does not retarget its references to a replacement at the same path/name. Retained authorized metadata may expose a tombstone with `availability: "deleted"`; missing/expired/restricted content is explicitly unavailable. A live execution's historical context binding survives as metadata to the extent retention permits. Context deletion neither proves that execution stopped nor automatically grants a new launch there. New work requires a live authorized context revision; inspection of unavailable historical inputs cannot certify an exact consumed source. Current context configuration alone cannot prove sealed inputs: [Product 02's binding levels](../product/02-work-evidence-and-coordination.md#revision-bound-validation) apply.

### Ordered event cuts and causal references

Keep causal relationships explicit: operation → admission → runner delivery → stream events → observation → validation decision. Every interactive session incarnation has one increasing event sequence, assigned by its canonical runner/keeper ordering boundary to output reads, delivery records, acknowledged geometry and state-relevant controls. An event reference includes session ID, incarnation and sequence; `0` is the empty prefix. An observation's `processed_frontier` is the contiguous prefix reduced by the engine, and may lag a separately identified `source_frontier`. Both cuts must name the same session/incarnation, with processed no later than source in that local sequence. An exact processed cut does not include unread output, application-internal state or an atomic view of the OS. Event numbers never restart within an incarnation; duplicate delivery of a record keeps its original identity.

Managed pipe work needs no session. Its event scope is the execution ID plus runner ID/incarnation, with an execution-local service observation sequence. `stdout` and `stderr` have independent stream epochs and half-open byte ranges `[start, end)`; their observed interleaving cannot prove the program's cross-stream write order. A PTY has one merged `pty` stream, not recoverable stdout/stderr attribution. Stream epoch changes retire offsets from the old stream. Byte offsets, event sequence and semantic revision measure different things and are never substituted for one another.

Each observation/range declares the projection and completeness **for that requested range/cut**, capture policy, gaps and availability. A retained prefix can be complete for its range while later output remains undrained. A missing canonical event cannot be skipped to advance the processed frontier; interpretation becomes unknown. A capture-only gap can coexist with a current live interpretation, but the missing bytes are unavailable evidence. Slow presentation consumers can resnapshot; neither frontend repairs a canonical gap locally. N0-06 owns frame base/target, paging/credit and resync envelopes.

Cross-session or cross-execution dependence cites a bounded list of explicit event cuts, operation records, or artifact/context revisions. Resolving a reference proves the stated record/prefix exists under its availability/trust limits; a causal edge means that dependency was selected, not that an observed redraw was caused by an earlier input. Unavailable references remain unresolved and cannot satisfy an inspectable-evidence requirement. Cyclic dependency selections conflict under [Product 02](../product/02-work-evidence-and-coordination.md#dependencies-and-coordination). There is no comparison between session A/event `9` and session B/event `3`, nor between two objects' revision numbers. Wall time is diagnostic, not a global event clock or a causal fence. Expiry uses the separately defined trusted clock boundary and is invalidated across service restart when continuity cannot be established.

One mediated application-input writer per interactive session; separate readers can observe with data grants. The canonical terminal reply lane has its own restricted authority and ordering. A human override atomically advances the writer epoch and rejects queued old-epoch input before dispatch. It does not retract already written bytes, revoke external credentials, stop all descendants or undo filesystem/network effects.

## Minimal operations and asynchronous outcomes

Use a small typed protocol, not an arbitrary remote object graph:

| Operation family | Required intent | Result and limits |
| --- | --- | --- |
| `CreateTask`, `StartAttempt` | Objective/acceptance and selected dependency revisions; expected task/context revisions and attempt limits | Task/attempt and operation IDs; later domain transitions. Task/attempt identity exists independently of a shell or process launch. |
| `RunProcess` | Task/attempt/context revisions; argv array; cwd/env policy; pipe/PTY choice; output/capture and runtime profile | Immediate execution/operation IDs; later started/exited/drained evidence. A shell command string is a separately authorized explicit shell execution, never inferred from argv. |
| `CreateInteractiveSession` | Shell/program argv; declared compatibility profile; geometry; runtime and capture policies | Session identity and negotiated capabilities. Existing-shell keystrokes are not equivalent to creating a managed process. |
| `Observe`, `Subscribe`, `ReadRange` | Explicit session or execution; requested projection; base/event cursor; data grant | Snapshot/delta/range plus completeness, gaps and availability. Credit-bounded; a stale cursor requests a new snapshot, not a guessed delta application. |
| `AcquireWriter`, `ReleaseWriter`, `TakeOver`, `Resize` | Expected epochs/context; endpoint; sizing policy where relevant | New epoch or typed rejection. UI attach/detach does not kill work. |
| `SendKey`, `CommitText`, `Paste`, `Mouse`, `FocusReport`, `SendRaw` | Distinct event type; explicit target; expected observation/profile/lease/focus/geometry; bounded payload | Receipt with encoded/delivered frontiers, later observed transitions. Raw is an explicit separately granted escape hatch, not a bypass. |
| `ViewCommand`, `ReadSelection` | Explicit endpoint/view, mapping/focus generation, bounded UI operation or identified range | Separate UI/observation/export capability; no application bytes, writer acquisition or implicit clipboard permission. Product focus changes are not terminal focus reports. |
| `QueryOperation` | Prior operation ID or exact issued request identity; current read authority | Reconcile retained metadata without resubmitting, including when an admission ACK and its operation ID were lost; expired or unavailable facts stay unknown. |
| `CancelOperation`, `SignalExecution`, `StopRuntime` | Target operation/execution/runtime identity, scope, escalation policy and grant | Cancellation requested/observed/no-longer-applicable/unknown. Process stop needs separate OS observations. |
| `RegisterArtifact`, `RecordValidation`, `RequestDecision`, `RecordDecision` | Authorized immutable object/evidence/context binding; expected request/subject revisions for a disposition | Inspectable provenance, freshness and decision state. Decision identity comes from the authenticated control channel. Arbitrary process output cannot invoke these methods or create grants. |

Long operations return a handle and publish status; waiting does not hold a writer lease or event-loop thread unnecessarily. `WaitFor` predicates are narrowly typed (specific execution exit, observed frontier, artifact revision, explicit adapter event), with timeout/cancellation. No generic “wait until terminal ready” predicate claims application readiness. Input context binds session/incarnation, host/helper and service authority epoch, endpoint/writer generation, observation and freshness policy, geometry/buffer generation, mode/profile/capability revision, known prompt/protection revision, action/approval reference, deadline and request ID. View-derived requests also bind mapping/focus generation; direct session input never requires human focus. Absent fields are not wildcard authority. Capabilities separately state representability, negotiation, authorization and endpoint limits.

Input batches are bounded sequences of operations, not atomic TUI transactions. Revalidate each not-yet-started event; fix its encoding before the first byte and never re-encode a partial suffix under changed modes. A takeover may discard the remaining suffix, leaving application state uncertain.

Illustrative managed launch shape, **not** an implemented wire schema or stable method spelling. All reference IDs inherit the envelope namespace:

```json
{
  "namespace_id": "ns-synthetic",
  "request_ref": "request-launch-1",
  "method": "RunProcess",
  "expected_authority_epoch": "7",
  "task": { "id": "task-check", "revision": "1" },
  "attempt": { "id": "attempt-a", "revision": "1" },
  "context": { "id": "ctx-demo", "revision": "3" },
  "process": {
    "argv": ["fixture-check", "--format", "json"],
    "cwd_policy": "context-root",
    "env_policy": "declared-nonsecret-fixture",
    "runtime_profile": "host-approved",
    "io": "pipes",
    "capture_policy": "memory-only-bounded"
  }
}
```

Authentication/capabilities come from the connection, not a caller-supplied principal label. An admitted response supplies an operation/execution ID and receipt cursor; later events bind exit, stdout/stderr ranges and drain status. The service resolves an authorized cwd/env/runtime policy from the context. A human can open a terminal for that context separately; no shell line or ANSI prompt is needed to identify the managed execution.

`Observe` selects an exact execution/runner or session/incarnation and a bounded projection; it returns a resolved subject, observation ID, processed cut and individually attributed facts. `RegisterArtifact` records an authorized immutable object revision, its producer attempt/execution, actual context/source binding and evidence references; it does not make a validation pass. `RequestDecision` selects exact task/artifact/validation revisions and creates a pending review record. `RecordDecision` requires an authenticated authorized disposition and expected pending-request/subject revisions; a stale selection conflicts instead of accepting a changed subject. None of these operations requires writing shell bytes or detecting a prompt. Product 02 owns validation quality, currentness and task acceptance; permission approval remains a separate broker operation.

Admission, dispatch, OS delivery, process lifecycle, observation and task acceptance are independent facts. [The receipt contract below](#receipt-admission-retention-and-reconciliation) replaces a single `success` flag with explicit evidence at each boundary. An `observed_transition` cites later state; causation may remain inferred when the application emits unrelated output. Process exit does not establish stream drain, descendant termination, validation or task acceptance.

## Receipt admission, retention and reconciliation

This is the authoritative N0-02 receipt draft, not a storage implementation, stable wire schema or an exactly-once external-effect promise. It covers every admitted mutation, including launches, input, signals, cancellation and domain decisions; read-only queries/subscriptions have no mutation identity. `request_ref` in the preserved N0-01 examples is an illustrative label for the issued identity below, not a client-chosen deduplication key. N0-06 must give these fields a separately versioned public spelling. Both human clients and native agents use the same service records and refusal rules.

### Issued identity and ordered admission

A mutation key is `(namespace_id, request_namespace_id, authority_epoch, request_seq)`. The object namespace follows the lifetime rules above. The service issues each **request namespace** to one authenticated principal in one authority epoch, with immutable `first_seq: "1"`, `max_seq`, `not_after` and a trusted clock origin. The registry is allowlisted: only currently issued namespaces are eligible for new admission. A syntactically plausible, unknown, deleted or retired namespace is never adopted from a caller. Namespace IDs are never reused, including after store reset/clone; issuance uses a durable nonreusing allocation cursor within its epoch, and refuses exhaustion. Loss of that allocator's continuity closes the epoch instead of risking reissuance. A request includes that exact issued key, its dispatch deadline no later than `not_after`, and all typed intent/precondition fields. Issuance is not an effect grant; current connection authority is checked separately.

Sequence/epoch fields use the canonical unsigned decimal strings above; `max_seq` is finite and nonzero, and exhaustion closes that namespace instead of wrapping. For each active namespace the durable ledger records `consumed_through`, initially `"0"`. Admission is serialized **within that namespace**: only `consumed_through + 1` can receive a new decision, and a larger sequence is refused without consuming it. Clients needing concurrent admission use separately issued namespaces within quota, or serialize admission ACKs and dispatch admitted work concurrently. Event clocks, operation IDs and another namespace's sequence do not advance this cursor.

Before any ledger mutation, the service authenticates the connection, verifies ownership and current submission authority for an active issued namespace, and checks canonical next identity, envelope/body shape, epoch, time and capacity. Unauthenticated/wrong-owner submissions, retired/unknown namespaces, malformed envelopes, future sequences and inability to durably reserve capacity consume nothing and dispatch nothing. Only an authenticated owned valid next identity can enter the decision transaction. The service checks its exact subject revisions and effect grants, then atomically consumes the sequence and records either an admitted operation plus reserved receipt slot, or a final rejected decision (for example, a stale subject or refused effect grant) with no external dispatch. It retains an exact volatile binding to that decision. If storage commit acknowledgement is lost, the caller must query; it cannot assume the transaction failed. Rejected consumed decisions can be compacted like receipts; their sequences remain closed. A preflight refusal is not such a consumed rejection.

Strict sequence order creates head-of-line blocking only inside its owning request namespace: a missing next sequence is refused without a wait queue or cursor advance. One agent cannot fill another principal's namespace allocation or cursor. The finite review model reserves per-principal capacity below; this receipt contract supplies no global dispatch latency/fairness guarantee. N0-09 must review scheduler fairness and reserved human-control capacity under the production limits, rather than claiming that ordered admission alone prevents starvation.

| Repeated or out-of-order submission | Required behavior; no row authorizes dispatch |
| --- | --- |
| `request_seq <= consumed_through`, exact binding still available and equal | Return the retained decision/operation reference under current read authority; this is lookup of the original decision. Never dispatch again, including when its delivery is zero. |
| Consumed sequence, binding available but any intent/precondition differs | Refuse payload conflict; retain the original decision and binding. A changed deadline, method, target, revision, epoch, policy, argv or input is a changed request. |
| Consumed sequence, binding missing, receipt pruned, or body equivalence cannot be established | Refuse repeated mutation without claiming equal/different bodies. Offer authorized metadata reconciliation; no comparison to a guessed hash and no new operation. |
| Unknown/retired namespace, old epoch, `now >= not_after`, sequence beyond `max_seq`, or future sequence | Refuse new admission. A retained historical decision can be queried separately. Time moving backward cannot reopen a namespace. |

Body equivalence is equality of the validated typed intent, including exact string/byte values, array order, resolved policy/subject references and preconditions, with specified defaults materialized once; JSON whitespace/key order and transport correlation IDs are excluded. Duplicate keys, unknown mutation fields and unsupported versions fail validation before this comparison. The binding and reserved metadata become visible to concurrent submitters at the decision boundary; if a binding allocation cannot be retained, repeated submissions take the missing-binding refusal path. A service restart issues a fresh authority epoch and closes all old request namespaces even if their clock would otherwise be valid. New work needs a newly issued namespace and fresh authority. Old queued controls must be fenced/reconciled before a new controller dispatches; advancing an epoch does not reverse in-flight writes.

`QueryOperation` accepts either an operation reference or the entire issued mutation key, uses current read authorization and never requires a replay body. Thus losing the admission ACK does not require guessing an operation ID. It returns an authorized retained decision and its evidence, or explicit unavailable/unknown with the last known reference where permitted. A query showing no retained receipt is not a certificate that no mutation occurred, nor a reservation against an in-flight admission. Old mutation grants are not resurrected for a historical read. The caller never resubmits merely because a query times out.

### Retention, finite budgets and privacy

Issuance/admission must expose finite `max_seq`, namespace lifetime, dispatch deadline, receipt-retention horizon and quotas for active namespaces, receipt slots and volatile bindings. These are negotiated receipt-profile values, not caller-selected authority. N0-06/N0-09 must encode/admit concrete product limits; unknown or unbounded limits refuse admission. The deliberately small review profile below makes the lifecycle examples finite without adopting production sizing or an input-encoding limit.

| Review profile `n0-receipt-model/0` | Bound for hand-authored traces / future finite exploration |
| --- | --- |
| Actors/namespaces/sequences | Two authenticated principals; at most two issued namespace ledger records per principal/four total, including closed records awaiting retirement; sequences `1`–`4` per namespace |
| Lifetime and reserved metadata | Namespace valid for five trusted model ticks; each consumed decision reserves one of at most four receipt slots per principal/eight total through ten ticks after decision, including a rejected decision |
| Payload binding | At most four volatile bindings per principal/eight total of 1024 validated representation bytes each; larger bodies or exhausted slots refuse admission in this model |
| Dispatch | Deadline is at most namespace expiry and strictly after admission; a first dispatch requires trusted `now < deadline`. A deadline stops a new dispatch, not effects already underway |

Production values require review before an engine advertises this contract; the model tick is an injected ordered clock step, not a latency measurement. Reserved slots are never silently evicted for new work. Capacity failure refuses new decisions before effects; a namespace cannot be renewed or its sequence reset in place. At namespace closure, no new decision can be admitted; at receipt expiry a query can lose detail, but every consumed sequence stays at or below its durable high-water until that namespace is retired. Retirement removes it from the issuance allowlist permanently and may occur immediately after closure; any remaining receipt remains independently queryable by its key under retention/read policy. Closed cursor records still count against the namespace-ledger quota until retirement, rather than accumulating without bound. These fences cover both receipt compaction and removal of the namespace ledger itself; a bounded ledger plus one nonreusing issuance cursor does not require an unbounded per-request tombstone set.

Before dropping an admitted receipt, prevent any not-yet-started dispatch from using it; already-started work may still have effects and its unavailable outcome must remain so. Receipt expiry is not process termination. Retention uses trusted monotone time with validated continuity; when that continuity is unavailable, close mutation namespaces and do not prune an outstanding reserved horizon merely from an untrusted wall clock. Finite storage may then refuse admission until retention can be resolved. Lost/corrupt identity or cursor metadata retires the entire affected namespace (and, if object-namespace continuity is unproven, replaces the object namespace); never reconstruct `consumed_through: "0"` under an old issued identity. A restored terminal snapshot cannot roll this ledger back or supply dispatch authority.

Default durable receipt metadata is bounded identity/status data: issued key, operation/typed target references, admission and dispatch phase, authority/controller epochs, trusted retention/deadline metadata, delivery extent/evidence reference, cancellation reference and sanitized reason. It excludes argv, environment values, input, encoded payload, arbitrary adapter output, request bodies, payload lengths that policy treats as sensitive, and their content-derived hashes. Keep full body/encoding binding in authorized volatile memory only, within the declared budget; clear it on expiry/revocation/restart. Even a salted hash can disclose low-entropy input and is not default-safe redaction. An explicit future input-audit policy needs separate consent, retention and secret-reference design; it is not enabled by this draft. Fixture integrity hashes identify public synthetic files, not stored request hashes.

### Dispatch evidence and transition table

Admission records `admitted` or `rejected`; dispatch records `not_started`, `started` or `closed` plus evidence; delivery records `pending`, `zero`, `partial`, `full`, `unknown` or `not_applicable`. These are orthogonal fields, not one lifecycle ordinal. Before contacting a runner, durably record dispatch intent with its operation/target/epoch metadata, and freeze encoding in authorized volatile state; no payload/hash is added to the durable record. The runner's final ordered boundary must validate current authority and writer/control epochs. An unacknowledged dispatch command is queried, never resent as permission to perform its effect. Transport duplicates cannot invoke the OS boundary again. N0-03 owns the writer/control interleaving algorithm; this contract requires the following outcomes from it.

For byte input, `full` means the entire nonempty frozen encoded byte sequence crossed the specified OS write boundary. `partial` means a known strict nonempty prefix crossed and dispatch is closed with no remaining write; `zero` requires authoritative evidence of no delivery and no remaining dispatch. An admitted intent whose frozen encoding is empty closes with `zero` without an OS write. `unknown` carries any proven lower bound/prefix and the uncertain remainder; missing evidence is never a zero count. While dispatch can continue, `pending` may carry a proven prefix. Public byte extents require authorized disclosure; where withheld, return restricted extent instead of fabricated zero. Nonbyte effects name their boundary: for a launch, `full` requires observed OS creation bound to its private stable handle, `zero` proves no launch, and `unknown` means creation cannot be established. A full signal receipt means OS acceptance against the exact stable target, not observed handling or termination. No byte count is invented for a signal/launch. A domain-only mutation has `not_applicable` external delivery and its own committed record; its lost ACK is still reconciled by identity.

| Prior fact / event | Permitted next fact and required proof |
| --- | --- |
| No durable admission/reservation; validation or storage failure | Reject/refuse with no dispatch. Missing commit ACK is unknown to the caller until queried, rather than proof of rejection. |
| Admitted, `not_started`, `pending` | Start once after final epoch/freshness/deadline check and durable dispatch intent; or close with `zero` when the ordered control boundary proves it never dispatched. |
| `started`, `pending`; OS boundary reports a prefix | Increase proven prefix monotonically; stay pending while more may be written. Freeze encoding throughout the operation; never splice a suffix encoded under new modes. |
| Started dispatch closes with authoritative extent | `zero`, strict-prefix `partial`, or `full`; evidence binds the same operation, runner incarnation, target and frozen encoding. A zero-delivered operation is still consumed and cannot be replayed. |
| Dispatch/runner ACK lost, crash cut or target evidence inaccessible | `unknown` with known prefix if any. Client-only response loss leaves the client's knowledge unknown without erasing a keeper's retained `full` record. |
| Unknown outcome; later verified same-operation runner record | Refine to zero/partial/full or a larger proven prefix. Prompt text, PID/argv similarity, timeout and absence of output cannot resolve it. No redispatch to obtain evidence. |
| Receipt/runner evidence expires or is deleted | Expose unavailable detail/last known references; do not rewrite a historical proven full delivery as zero or make its key reusable. |
| Full delivery, later exit/drain/output/validation/decision | Append separately attributed facts. Full write is not proof that the application consumed bytes or accepted intent; exit is not drain, drain is not validation, validation is not task acceptance. |

There is no transaction spanning the durable admission/dispatch log and OS effects. A service/helper crash between an OS write or process creation and its durable result can therefore leave an unknown outcome permanently. This contract prevents a duplicate identity from becoming permission to execute again; it does not prevent arbitrary applications from repeating their own effects or make a newly authorized attempt safe after uncertainty.

### Cancellation, expiry and takeover

Canceling a wait or subscription releases that wait/credits. A client disconnect is not cancellation of its admitted effects; lease release follows writer policy. `CancelOperation` is a separate admitted mutation, with its own issued key/receipt, exact target operation and current authorization. Its request ACK means cancellation was requested/recorded; only an ordered dispatch-boundary acknowledgement can establish what it stopped. Before first dispatch, confirmed closure gives the target `zero`. After a prefix or in-flight OS call, closure gives proven `partial`/`full` or `unknown`; a cancellation timeout alone proves none of these. If no longer applicable, report that disposition without changing the target's delivery. Stopping a created process/runtime requires separately authorized controls and observed lifecycle facts; cancellation of its launch receipt does not terminate it.

Expiry, revocation and human takeover use the same distinction between preventing a new dispatch and accounting for an already-started effect. A new writer epoch fences queued old-epoch input at the final ordered boundary; it does not retract a delivered prefix, erase a launched process, stop descendants, accept a task or undo files/network effects. Both TUI and Electron must show the target's residual partial/unknown effects separately from the cancellation/takeover receipt. Application or prompt bytes that resemble an ACK, decision or cancellation have no authority.

### N0-02 review traces and future assertions

Synthetic receipt data in `tests/fixtures/native-receipts/` owns local provenance/integrity only; the rules remain here. `valid-lifecycle.json` separates admission, response loss, exact duplicate lookup, changed-body refusal and exit/drain/acceptance. `valid-retention.json` covers restart, binding loss, expiry/compaction and lost identity history. `valid-cancellation.json` covers queued cancellation, partial takeover and unknown in-flight dispatch. `invalid-cases.json` independently proposes forbidden transitions. All are hand-authored review oracles, not executed model tests, a schema, implementation evidence or NG0 acceptance.

| Assertion / V family | Required future falsification under injected scheduling, clocks, crashes and storage faults |
| --- | --- |
| RC01 / V01–V02 | For each issued key, at most one admitted operation and at most one logical dispatch start exist; exact duplicate lookup, including after lost ACK or known zero delivery, never adds an OS effect. |
| RC02 / V02 | Changing any bound field of a consumed key conflicts when binding exists; removing the binding changes this to refusal, never equality, new admission or a persistent secret/hash. |
| RC03 / V02 | Gaps, wrong principal/epoch, unknown/retired namespace and exhausted sequence cannot advance `consumed_through`; concurrent next-sequence submissions serialize to one decision. |
| RC04 / V01–V02 | Every dispatch has a committed admission, reserved metadata and durable dispatch intent; no effect precedes either prerequisite commit. Lost commit/result ACK is reconciled without resend. |
| RC05 / V02 | Pruning receipts, namespace retirement, backward time, restart or restoring an older terminal snapshot never permits a consumed key to become a new mutation. Missing identity/cursor continuity retires its namespace. |
| RC06 / V01–V03 | Across every crash cut around OS calls, zero/partial/full are asserted only from same-operation boundary evidence; otherwise expose unknown with monotone known prefix and no automatic replay. |
| RC07 / V03 | Ordered cancellation/takeover before first dispatch proves zero; after first write, preserve exact prefix or uncertainty and refuse stale remaining work. No cancellation ACK, lease change or timeout claims rollback. |
| RC08 / V01–V03 | Launch delivery, process exit, stream drain, observed transition, cancellation and task acceptance can vary independently; prompt-shaped bytes cannot advance any control/domain record. |
| RC09 / V01–V02 | Exhaust each namespace/receipt/binding quota and expiry boundary (`now == deadline` included); fail before new effects without evicting reserved records, wrapping counters or extending an old namespace. |
| RC10 / V02–V03 | A current authorized query by request key works after lost operation-ID ACK and after epoch change without replay body/old grants; unavailable evidence remains unavailable in both clients. |

The future independent model must enumerate the small profile's admissible interleavings and challenge these oracles, including delayed old-controller frames and crash cuts before/after consumption, dispatch intent, OS effect and delivery-record commit. It must also cover nonbyte operations and metadata-only rejection/cancellation, rather than treating every effect as a successful byte write. N0-03 must add its writer ownership traces and N0-06 the public/client shape; N0-02 alone cannot close those seams.

## Observation and evidence schema

An observation envelope contains identities/epochs, engine/profile/Unicode versions, processed input/output/resize event cuts, capture classification, geometry/active buffer, cell/grapheme/styles/cursor and supported mode metadata. Large history/artifact projections are paged with stable IDs; snapshots and deltas share base/target revisions. Agents request bounded task/stream/cell/range projections instead of receiving every pane or unbounded transcript. Keep model-specific tokenization/inference outside the core, and preserve evidence IDs when selecting or summarizing context. A slow subscriber may skip presentation frames and receive `resync_required`; it may not silently skip canonical parser input.

Every status carries one of:

- **Observed by an authorized component:** OS child exit, bytes read, canonical cell/mode state, broker grant/lease, immutable artifact digest, completed validation with exact inputs.
- **Reported by a cooperative application/adapter:** command boundary, progress, native plan or semantic widget. Record producer identity/schema and trust; authenticate the channel but do not assume the producer tells the truth.
- **Inferred:** prompt detection, OCR, likely TUI selection, apparent readiness or causal attribution. Record method and evidence, never elevate to permission or OS fact.
- **Unavailable/unknown:** capture denied, retention gap, state lost, output not drained, stale geometry or unreachable runner. These are valid results.

The fact discriminator is mandatory per claim, not a label inherited from a whole transcript. Each available fact records its typed subject, producer component identity/incarnation, source event/range or authenticated control record, and relevant schema/method version. Cooperative reports also identify the authenticated producer channel/schema and its trust limits; inference names its method and underlying evidence. `unavailable` supplies a reason and last-known reference where authorized, with no invented value. Absence of an exit fact means unknown, not exit code zero. A fact can remain attributed while its supporting content becomes unavailable; inspectability and truth are separate properties.

Observation by the runner establishes, for example, that bytes were read or a child exit was observed at its OS boundary. Observation by the service establishes that an authenticated decision was recorded, not that the decision's claims about arbitrary files are correct. An authenticated adapter's `check_passed` remains **reported** unless a separately authorized validator supplies its own exact-input evidence. A digest establishes identity of the authorized retained representation, not its correctness. Output text/OSC resembling JSON methods, principal names, approval messages or native event names remains application data. It cannot create a managed execution ID, upgrade a report to an observed OS fact, grant authority, or accept a task. Prompt detection remains inferred even when a heuristic is usually right.

Native structured output uses a separately authenticated, bounded side channel, associated with an execution/attempt and constrained event schemas. It can supply domain-specific data without reverse parsing ANSI. It cannot change the supervisor's permissions or self-certify an artifact's acceptance. OSC prompt markers use the weaker compatibility hint path even if they resemble native event names.

## Observe–act–observe, races and human override

1. Observe explicit session S/incarnation I at frontier F, geometry G, mode/profile P. Select a bounded action justified by that evidence. Unknown opaque-TUI focus is still unknown.
2. Submit the target, writer epoch, capability, action ID and freshness policy. The broker rechecks context/approval and the engine serializes encoding against canonical mode state. Coordinate actions require matching geometry and screen revision; stronger screen-bound actions require exact frontier. Output churn returns `stale`, not silent revalidation.
3. At the runner's final input queue, recheck writer/authority epoch immediately before the first write. Takeover and dispatch use one ordered control channel; acknowledgements establish what was fenced. A write already underway may finish partly, so report its prefix or uncertainty. No global “atomic user click” claim.
4. Observe the resulting frontier/receipt. If the expected transition is absent, distinguish delivery unknown, no change, unrelated output, unsupported input and wrong inferred app state. Do not repeat a non-idempotent action to make the screenshot look right.

Strict screen-bound actions can starve on a continuously updating screen. Offer an explicit owner-approved session-level interaction grant with weaker freshness and visible uncertainty, or human control; do not quietly widen the action's authority. Human input may use that interactive policy, while sensitive approvals remain revision-bound protected UI operations. Keyboard modifiers, release/repeat, IME and lost host facts follow the [input profile](compatibility-and-core.md#input-policy).

There is no OS primitive that atomically compares an application's screen/widget state with delivery of a key. The backend's processed frontier can be current to its event cut while newer output is unread or the application changes internally without output. An exact revision fence is therefore a real backend guarantee, not an atomic TUI transaction. Cooperative typed application operations can supply stronger semantics; opaque interaction retains this race and must use an appropriate uncertainty grant or human intervention.

## Coordination and integration limits

Parallel agents own separate attempts/processes/interactive writers by default. Dependencies become ready only at recorded revisions. A group budget constrains admissions, output, retained evidence and concurrency; it is not a claim to control an agent's unmediated provider/network calls. Conflicting worktrees/artifact publication need an explicit integration decision. One agent cannot mutate another's writer context by changing a task label.

ACP/MCP adapters are optional later consumers of this contract, not foundational dependencies. Map cancellation and lifecycle semantics explicitly: ACP v1 `terminal/release` kills a running command (S17), while namtab detach does not. Foreign output truncation must become a gap, and foreign task completion must retain its trust level. No automatic mapping from an external permission request to an internal grant. Native APIs remain useful with a deterministic local client and no model provider.
