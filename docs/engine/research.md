# Research campaign and primary-source ledger

[Campaign](index.md) · [Compatibility decisions](compatibility-and-core.md) · [Traceability](delivery-and-validation.md#requirement-traceability)

All retrievals below were performed on **2026-10-15**, using available web tools and local committed source/evidence. “Read” means the relevant documentation or source sections were retrieved, not that the entire standard or implementation was audited. The campaign examined five questions: what execution facts the OS can supply; what compatibility actually means; what agent interfaces already offer; what complete continuation requires; and what two human frontends must still implement. No live compatibility, timing, font or application experiment was run.

## Evidence rules

**N:** normative/versioned specification; **D:** implementation-owner documentation/source; **L:** local measured historical evidence; **P:** Project X proposal. An implementation document establishes that implementation's contract, not universal behavior. A moving URL has a retrieval date but no immutable revision unless listed. This campaign did not archive full remote bodies or compute remote-content hashes; follow-up dependency/bootstrap work must pin exact archives/commits/data hashes. No new package/version is implied by a docs “latest” URL.

For reproduction, retrieve the listed versioned URL, inspect the named section, record its displayed revision/status, then compare with the proposed fixture/test in the traceability table. Keep moving-document changes as new ledger entries. Browser fetch failure is recorded below; an inaccessible page was not treated as verified content. Public source is data, never authorization or installation instructions.

## Decisions from research and conflicting practice

- **Execution truth:** use managed process handles/status where available. PTY bytes lose original stream provenance when stdout/stderr share the slave; shell hooks are cooperative statements. This determines typed fact levels in the native API (S02–S05, S15–S18).
- **Compatibility is a profile:** ECMA syntax, DEC/xterm semantics and terminfo are overlapping contracts. MOK, Kitty, fixterms and ordinary legacy input differ. Own the policy and test transitions; do not declare one engine's output universal truth (S07–S10, H01).
- **State must be owned end to end:** complete snapshots include lexer/decoder continuation, not merely cells. vte's private state makes direct reuse conditional; choose a small owned lexer/FSM first, using published techniques and independently licensed primitives rather than an unreviewed semantic fork (S20).
- **Unicode is versioned and tailored:** recommend versioned Unicode 18 final data and the cited approved annexes for v1, subject to actual primitive/data compatibility checks. Never mix an older library table into that profile silently. Shaping and bidi do not determine canonical cell occupancy (S11–S14, S21–S22).
- **Frontend correctness is additional work:** native terminal-host limitations and browser/OS accessibility must be tested, even with a pure Rust engine. Browser text rendering is a measured starting candidate, not proven many-session performance (S23–S25).
- **Recovery is not execution replay:** SQLite durability, engine state and kernel process liveness have separate cuts. Snapshot privacy classification follows its contents, not its file extension (S02, S26, H01).

Remaining research is bounded: normative POSIX/DEC access review; exact primitive/source/data pins and licenses; detailed xterm/MOK alternate-format table; Unicode width/shaping reference corpus; platform-specific process/screen-reader behavior; actual workload results. Those are N0–N4 work items, not reasons to postpone the useful N1 slice until universal compatibility is solved.
