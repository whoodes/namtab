## Selection posture

**Recommended next prototype:** Rust Ratatui/Crossterm host TUI and Electron TS/React desktop, sharing a native canonical libghostty-vt worker and owned semantic/cell rendering. The core public API and same-build snapshots have bounded proof; real rendering, FFI, input/accessibility, resources and upgrades remain unqualified. Revised xterm is a credible fallback. This is a deliberate renderer investment, not a universal performance ranking; see ADR E1 and 19.

The host TUI draws canonical cells rather than emulating inner output and shares the broker API. Optional shell/prompt themes are separate, with no Zsh requirement. [TUI framework comparison](../engineering/15-dependencies-and-supply-chain.md#rust-tui-choice) recommends Ratatui/Crossterm over adding a widget/component framework initially. [14](../engineering/14-repository-and-engineering-practices.md#jsts-workspace-and-build-choice) compares JS workspace managers and selects pnpm; [15](../engineering/15-dependencies-and-supply-chain.md) inventories proposed direct dependencies and unknown shipping versions.

PP1/X1–X6 can veto the core choice: the inspected public headless API does not establish a complete logical-key encoder or full checkpoint API. PP2/PP3 can veto the frontend on accessibility or resources. Do not purchase portability with degraded ordinary-terminal behavior. That statement described the earlier documentation phase; authorized local engineering and assessment evidence now exist in 18/19.

Evaluation priorities remain correctness, authority/lifecycle, human accessibility, maintenance, then resource/packaging tradeoffs. No numerical scoring substitutes for hard gates. No latency, memory, fidelity ranking or development-effort measurement has been invented.

These are credible alternatives, not equally ready drop-in components. Maturity of a terminal application differs from maturity of its embeddable API. Platform claims below describe upstream surfaces, not a certified Project X port.

## Core/renderer selection and measured vetoes

Use one pinned public native core and versioned semantic/cell frames in both views under ADR E1. The bounded Ghostty proof passed state/input cases; real render-state performance and accessible rendering remain gates. The earlier xterm family is retained as a reference/REDESIGN alternative, not silently used as a second parser. Details and source provenance are in [19](../engineering/19-engine-build-adopt-redesign-assessment.md).

Compare on the same N01–N16 and J01–J08 cases, full resource accounting and failure corpus. Hard gates: canonical key encoding without global focus, no duplicate replies/bypass input, faithful replica at known prefix, bounded parsing and recovery, full keyboard/IME/assistive navigation, and G6 load. A candidate failing authority/correctness cannot win by using less RAM. A view serializer cannot be promoted to a complete canonical checkpoint without evidence. Reject a continuing custom parser fork or spread private API usage; a single pinned bridge may be acceptable only after an upgrade rehearsal.

The comparative assessment is complete for bounded A/B seams. The current next prototype is libghostty-vt + owned semantic rendering, retaining Electron and host TUI; revised xterm is the fallback. Electron footprint could justify a later Tauri comparison, and Linux-only accessibility could justify an explicit GTK/VTE scope choice. Neither changes the engine problem automatically. Ownership/fork triggers and staffing are in 19; build only one product core, not four competing engines.

## Language and reuse decisions

Rust owns admission, domain state, SQLite, process identity, CLI/TUI and native runtime adapters. The TUI uses a public Rust client and cannot import service/platform/store internals; its outer-terminal event decoder is distinct from the shared inner encoder. TypeScript owns React/Electron UI and public client code; the revised engine host is native Rust with an audited libghostty-vt C boundary, not the UI window. The engine host is not the UI main window and must survive its loss independently. No JS-enabled renderer receives process launch/PTY/file authority; narrowly validated IPC mediates intent. Keepers remain small, and one engine host multiplexes sessions. Exact module/process ownership is in [05](../architecture/05-architecture-storage-and-extensions.md).

Go is credible for a supervisor but would not remove TypeScript/native-engine integration and would give up the chosen Rust ownership/FFI ecosystem without evidence of a team benefit. C++/Zig have useful native ecosystems but add memory/toolchain/staffing responsibilities at this stage. Owned rendering now explicitly carries text/accessibility work; rewriting the rest of the UI in Rust would not remove that cost. No language is declared inherently secure or universally faster. Revisit if staffing cannot maintain the two-language baseline, not to satisfy a speculative monolingual preference.

Reuse SQLite for local transactional metadata, system OpenSSH for ordinary transport, Git worktrees for edit organization, and rootless Podman for the first restricted Linux profile. All are adapters with honest limits. tmux control mode is an optional remote/external-session adapter, not the primary ownership/persistence backend: outside writers and different interpretation boundaries weaken our guarantees. libvterm remains a compact C core alternative but does not supply the missing rich UI; the inspected Neovim fork is archived. [SQLite WAL](https://www.sqlite.org/wal.html), [OpenSSH](https://man.openbsd.org/ssh), [Git worktree](https://git-scm.com/docs/git-worktree), [Podman rootless](https://docs.podman.io/en/latest/markdown/podman.1.html#rootless-mode), [tmux control mode](https://github.com/tmux/tmux/wiki/Control-Mode), [libvterm](https://www.leonerd.org.uk/code/libvterm/), [archived fork](https://github.com/neovim/libvterm)

## Packaging and licensing

Recommend two aligned native Ubuntu package artifacts first: core/CLI/TUI including the qualified native engine, and desktop depending on that exact core product tuple. TUI-only use has no Electron/display-server requirement. The first complete terminal product includes both clients; a core-only installation is a legitimate deployment shape, not delayed TUI scope. Target x86_64, built against 24.04 LTS userland and certified on maintained 24.04/26.04; Wayland primary, X11 tested. Exact glibc/kernel/dependency patch floors await PP7, not this VM's uninspected capabilities. ARM64 later. Eventual macOS Apple Silicon/Windows 11 x64 ports retain the UI/domain, with native lifecycle, credentials, PTY/ConPTY and runtime adapters. WSL and remote Linux containers are distinct targets. [Platform ADR](../architecture/10-recommended-baseline-and-adrs.md#adr-a4-linux-and-eventual-desktop-ports)

Bundle Electron and the qualified native engine; Node remains a pinned build/assessment tool and Electron embeds its own runtime. The old separate Node engine runtime is not a shipping requirement under ADR E1. Monitor Electron's short release/update cycle and Node LTS policy; no frozen dependency version is promised indefinitely. Conventional native packages are the first release path. AppImage-style bundles remain a transport alternative. Flatpak's restricted host access requires deliberate host bridging for host-shell expectations; the desktop sandbox would not sandbox a launched host shell. [Electron timelines](https://www.electronjs.org/docs/latest/tutorial/electron-timelines), [Node releases](https://nodejs.org/en/about/previous-releases), [Flatpak permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html)

Installation does not change rc files, shell, default terminal, SSH config or privilege policy. User service starts on demand; quit/logout/update behavior is specified, not inherited accidentally from the service manager. Removal offers metadata export/retention and never deletes user workspaces by default. Signed releases, dependency provenance/SBOM, offline update/rollback and reproducible-build assessment belong to PP7; none is claimed complete. Update signatures establish origin, not behavior. Basic use needs no account/telemetry. Local diagnostics and opt-in uploads obey capture policy; no raw core-dump bypass.

Recommend **Apache-2.0 for Project X**, owner decision pending; MIT is the simpler permissive alternative. No LICENSE file is created. Patent-license clarity is the design reason, not legal advice or transitive clearance. Inventory every release's runtime, addons, crates, fonts and native components and preserve notices. Avoid bundled fonts initially. [License ADR](../architecture/10-recommended-baseline-and-adrs.md#adr-a8-license-and-dependency-maintenance), [Apache text](https://www.apache.org/licenses/LICENSE-2.0.txt)

## Compatibility matrix

All statuses below are planned support tiers, not test results. **Core** means a future release gate; **enhanced** needs an optional negotiated adapter; **conditional** depends on host/runtime capabilities; **deferred** is outside MVP. Version pinning and actual pass/fail records belong to a future test report.

| Surface | Planned tier | Required behavior / known limit |
| --- | --- | --- |
| Initial host-terminal TUI and Electron desktop | Core, same broker authority | DF01–DF08, safe canonical TUI rendering, no private store/PTY/engine access; physical keys/accessibility differ honestly |
| Outer TERM/color/font profiles and nested TUI prefixes | Core declared host profiles | Separate outer versus inner TERM, bracketed paste and sizing; explicit aliases/unknowns, ASCII/mono/linear fallbacks; no mandatory font/theme/Zsh |

| POSIX sh, dash, custom shells | Core terminal behavior | No universal structured command lifecycle |

| Raw-mode debuggers and programs using `/dev/tty` | Core host mode | Preserve controlling terminal; restricted runtime policies may limit ptrace/devices |
| tmux/screen nested inside Project X | Core basic operation | TERM/nesting tested; external writers reduce supervision guarantees |
| Existing venvs, library paths, custom toolchains | Core host mode | Preserve selected inherited context; isolated images are a different environment |
| Rootless containers/namespaces/cgroups | Conditional | Capability negotiation and tests; strict grants rejected if unavailable |

| Agent CLI with no adapter | Core opaque PTY/process | No inferred task success or trustworthy per-tool approvals |

| Agentic key/text/control navigation | Core, independent of agent adapters | Arrows, Tab/completion, Shift-Tab, editing/page keys, F1–F12 and representable modifiers; unsupported/aliased combinations disclosed |

## Compatibility contract

Advertise a truthful TERM/terminfo profile supported by the selected engine. A custom terminfo entry can be packaged locally but cannot be assumed present on every SSH host; document a conservative fallback and its feature loss. Do not claim a feature solely because an escape sequence is recognized. Existing applications must see coherent query replies, input encoding, color support, geometry, and nesting behavior. The xterm control-sequence reference is a useful primary compatibility corpus, not a universal complete specification. [xterm reference](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)

Initial host TUI over SSH to an explicitly installed remote Project X backend is distinct from opaque SSH inside a managed session and later helper transport. Outer emulator/tmux retention is not controlled by Project X memory-only capture.

Certification must include versions of shell/app/runtime, distro, terminal core, fonts/width profile, locale, display server, and capture mode. A compatibility bug report can carry a minimized byte/resize fixture without automatically exporting secrets or executing it as a shell script. Performance and accessibility remain release requirements, not optional polish after feature completion.
